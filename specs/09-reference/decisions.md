# Decisions and open questions

## Decisions

| # | Question | Decision |
| --- | --- | --- |
| 1 | Seatbelt depends on deprecated Apple interfaces | Keep Seatbelt as the baseline on every supported macOS. Codex CLI, Claude Code, Chromium and VS Code rely on it, so removal without a replacement is unlikely. `knsh-exec` runs Apple's `sandbox-exec` tool with the profile in a private file (`-f`), as those projects do, instead of calling private functions; a file also avoids command-line length limits. On macOS 27 and later, the Endpoint Security descendant client (decision 3) is a second layer and the fallback if Seatbelt is ever removed. |
| 2 | Name checks | Not a design question; moved to the launch checklist: EU and US trademark searches for Kinetic Shell, domain, Homebrew formula name, the `kinetic-shell` crate and a GitHub organisation, all before any public announcement. |
| 3 | Per-command decisions for binaries run directly inside an envelope | Pursue on macOS 27 and later with `es_new_descendants_client`: an Endpoint Security client scoped to the process subtree it starts, needing neither root nor privacy approval, which Apple describes as built for constraining agents. `knshd` starts every envelope, so envelopes are its descendants, and it can decide every exec inside them, including `/bin/bash` by absolute path. It needs Apple's Endpoint Security entitlement: apply now. On macOS 14 to 26, the envelope alone confines direct execution. KNSH-094 implements the mechanism (probe value `seatbelt+endpoint_security`, one client per envelope, exec decisions through the supervisor's pipeline, deny at the deadline; [agent integration](../03-functional-requirements/agent-integration.md#exec-decisions-through-endpoint-security-knsh-094)); the macOS binding stays unavailable until the API is verified on macOS 27 with the entitlement. |
| 4 | Agents as a separate macOS user | Not in the first release. It needs a root helper, which breaks the no-root design, and causes file-ownership friction with projects, git and caches. Envelopes, per-command profiles and the descendant client cover most of the benefit. Revisit for managed enterprise deployments. |
| 5 | Encrypting the stores | FileVault plus user-only permissions is enough for records: they hold no secret values and output recording is off by default, and encrypting SQLite would need a third-party library. Checkpoints are the real exposure, because deleted secret files persist: files matching sensitive patterns (`.env*`, `*.pem`, `*.key`, `id_*`) are kept for 24 hours at most, and `knsh forget --with-checkpoints` removes them at once. |
| 6 | Parser scope for phase 2 | Exact: simple commands, assignments before a command, pipelines, `&&`, `\|\|`, `;`, `&`, redirections, every quoting form, command substitution and backticks (parsed recursively), subshells, `{ }` groups, `if`, `for`, `while`, `until`, `case` and function definitions. Dynamic: `eval`, `source` and `.`, command names built from expansions, `coproc`, here-documents fed to shells or interpreters, and anything the parser cannot read. Exit criterion: at least 95% of corpus lines parsed exactly, with every line's accept or reject verdict matching bash in differential tests. |
| 7 | Agent-command corpus | No user telemetry. Sources: published agent trajectories from public coding benchmarks where licences allow; traces from running supported agent CLIs on open-source repositories in CI; later, an opt-in `knsh corpus export` that shows the user every line before sharing. Every line is normalised: paths, user names, hosts and anything secret-like become placeholders. |
| 8 | Process information and signals: "own process group" cannot be enforced safely (KNSH-025, C8) | **Proposed.** Limit both to the process's **own sandbox** instead of its process group. Seatbelt's `(target pgrp)` also covers unsandboxed processes in the group, and a sandboxed process can `setpgid(2)` into another group of its session and then signal it. `(target same-sandbox)` has neither problem. Process information needs two rules, because another process's arguments and `kinfo_proc` stay readable while either rule allows them: `process-info*` limited to the same sandbox, plus `sysctl-read` denied for the `kern.procargs` and `kern.proc.` prefixes. Consequences: the system-wide process list (`proc_listpids`, `KERN_PROC_ALL`) is hidden, `ps` and other setuid tools cannot run in any profile, and an envelope cannot signal the lines the supervisor starts (separate sandboxes), so interrupting them goes through `agent.sock`. The same two rules hide other processes' environment: macOS 26.6 withholds it on its own only for Apple platform binaries, not for the tools an agent runs. The [sandbox profiles](../03-functional-requirements/sandbox-profiles.md) table is updated to match. |
| 9 | Tags and reporting of denials (KNSH-025, C2) | **Proposed.** The compiler gives every operation knsh relies on (the fixed denies, sockets, services, process information, job creation) an **explicit** deny rule with its own tag. It never relies on the tag of `(deny default)`: `job-creation` reached through the default was logged untagged, and built-in refusals (`forbidden-exec-sugid`) never carry a tag. Each tag names the session, the command (record) and the rule, so a supervised line's denial can be attributed by tag alone. Inside an envelope, only the session can be named. Violation reporting (FR-SBX-08) stays best effort, and the reader must handle known gaps: signal denials are never logged; denied access to a missing path returns `ENOENT` and is not logged; entries are occasionally dropped by the system; and `log stream` delivers nothing until it is attached, so the reader confirms it is live with a canary denial. KNSH-047 implements the reader on these terms: an entry is attributed only by an exact tag on the last of exactly two message lines from the kernel (`processID` 0, `/kernel`), and liveness is reported as `capabilities.sandbox_violations`. |
| 10 | Tools that apply their own sandbox inside an envelope (KNSH-025, C1) | **Proposed.** Confirmed on macOS 26.6: a sandboxed process cannot apply a different sandbox. The agent presets (KNSH-058) and the trusted-tools compatibility list (KNSH-076) turn each tool's own sandbox off inside envelopes: Chromium and Chrome `--no-sandbox`, Playwright's default `chromiumSandbox: false`, SwiftPM `--disable-sandbox`, Claude Code `sandbox.enabled: false`, and Codex CLI `--sandbox danger-full-access` (still to verify). Claude Code with its sandbox on lets the model retry a failed command unsandboxed unless `allowUnsandboxedCommands` is false, so a preset must not rely on that setting either way. Full app bundles (Chrome.app) abort without LaunchServices, which envelopes deny; the headless shell runs without it. Such apps run only as trusted tools (FR-SBX-09). |
| 11 | Which Keychain mechanism protects the policy signing key, the trust record and secrets (KNSH-026, C5) | **Proposed.** `knsh-platform` uses the **file-based (legacy) login keychain** with the default access list `SecItemAdd` creates, from a **Developer ID-signed** `knshd`. The item then trusts `knshd`'s designated requirement (identifier and team) with partition `teamid:<team>`, so every later Developer ID build reads it and nothing else does. Rules: (1) `knshd` never lets the Keychain show its "allow access" dialog (user interaction disabled), because a click there would hand the item to another program; a failure is a failure. (2) Any same-user process can overwrite an item's value; code outside the team then changes the partition list and `knshd`'s read fails (an overwrite by code of the same team is read back without error), so **a read failure on an existing item is tampering**: `knshd` fails closed for agents and reports it, and recovery (a new key, re-signing policy, trusting the authority again) needs Touch ID or the password. (3) Every profile adds a **fixed write deny on `~/Library/Keychains`**, because the client process writes the keychain files itself: with that deny an agent cannot overwrite, plant or pre-seed an item, and can still read its own items. (4) **Ad-hoc and Homebrew-from-source builds** are trusted by code hash, so each upgrade loses every item: such a build reports the Keychain-backed features as degraded in `hello`, and the user re-creates the key and re-trusts the authority after each upgrade. The supported Homebrew route installs the Developer ID release. The **data-protection keychain** with a team access group would also stop overwrites, but needs `knshd` inside an app bundle with a Developer ID provisioning profile (restricted entitlement; AMFI kills a bare binary); move to it if `knshd` ships as a bundle, after verifying it. |
| 12 | Approvals without a usable GUI session, and the prompt text (KNSH-026, C6) | **Proposed.** Fail closed. A launchd agent can show the LocalAuthentication prompt, and the dialog went to the console even from a job whose security session had no graphics access, so `knshd` cannot learn "no GUI" from an error: every outcome other than success (cancel, failure, lockout, an error, or no answer by the request's `timeout_at`) denies, with the reason in the record and on stderr (for example "not authenticated: no answer at the Mac's screen before the timeout"). `knshd` invalidates the context at the timeout. `knsh approve` from an SSH login says that the prompt appears on the Mac's screen. The dialog is titled with the process name and starts "knshd is trying to", so the reason text is written to follow it ("approve the agent command: <command> (cwd <dir>, session <id>)"); the command is shown in full, and a length limit for very long commands is still to be set. Characters that would not show or would change the display (control characters, bidirectional overrides, zero-width and other invisible characters such as tag characters, spaces other than the ASCII space, non-UTF-8 path bytes) are escaped, and backslashes are doubled so every escape is unambiguous (KNSH-064). With the lid closed, the prompt offers only the password, even though Touch ID is reported available. |
| 13 | XPC peer verification on macOS 14+ (KNSH-026, C7) | **Proposed.** `knshd` sets `xpc_connection_set_peer_code_signing_requirement` (macOS 12+) on every peer connection, with the FR-AUTH-13 requirement: `anchor apple generic`, the trusted team and identifier, the Developer ID or Mac App Store certificate markers, and `!(entitlement["com.apple.security.get-task-allow"] exists)`. On every message, not only the first (a peer can exec after its first message was accepted), it also calls `SecCodeCreateWithXPCMessage` and checks hardened runtime (signature flag), the live status (`CS_GET_TASK_ALLOW`, `CS_DEBUGGED`) and `CFBundleVersion` against the minimum (FR-AUTH-14); a connection failing any check is cancelled before the message is processed. Never identify a peer by pid: a process can send, then exec a trusted binary under the same pid. The authority sets the same kind of requirement for `knshd`, but the requirement only guards what the client *receives*: its first message reaches whoever holds the name. So the authority's first message is a `hello` carrying nothing sensitive, and it sends anything else only after a reply has passed the requirement (FR-AUTH-15 is read that way). launchd gives the control service name to the first job that declares it, so a job loaded before `knshd`'s could hold it; envelopes cannot create launchd jobs, and the authority's check catches anyone else. The authority's bundle needs a `CFBundleVersion` bound into its signature. |
| 14 | Per-command proxy credential transport and preset proxy settings (KNSH-027, C9, C10) | **Proposed.** Each line and envelope gets its proxy credentials as the user and password of an **HTTP proxy URL**, `http://knsh-<id>:<token>@127.0.0.1:<port>`, the only transport that worked for curl, git, npm, pip, cargo and Node. The token uses only letters and digits, so no tool has to percent-decode it. The environment of every line sets `HTTPS_PROXY`, `https_proxy`, `HTTP_PROXY` and `http_proxy` to it, removes any inherited `ALL_PROXY`, `all_proxy`, `NO_PROXY` and `no_proxy`, and adds `NODE_USE_ENV_PROXY=1` (Node ignores the variables without it) and `GIT_HTTP_PROXY_AUTHMETHOD=basic` (git otherwise waits for a challenge, one extra round trip per connection). Presets may also set `npm_config_https_proxy`, `npm_config_proxy`, `PIP_PROXY` and `CARGO_HTTP_PROXY` to the same URL. The proxy (KNSH-059) answers a request without credentials with `407` and `Proxy-Authenticate: Basic realm="knsh"`, and accepts only the Basic scheme. SOCKS5 with RFC 1929 username and password stays supported for tools that only speak SOCKS, with the same token as password, but is never the default: pip without PySocks and Node fail on it. Tools that ignore every setting (Node 22.20 and older releases without `NODE_USE_ENV_PROXY`, git over SSH) are refused by the profile, not leaked. |
| 15 | How the initial shadow of a root is built (KNSH-077, C3) | **Proposed.** Per-file cloning as FR-CKP-01 says, on a pool of **4 threads at QoS utility**. Observed on macOS 26.6 (M1 Pro, internal SSD, warm cache) for 100,000 files and 3,906 folders: 7.4 to 7.7 s, inside NFR-PERF-06's 10 s; one thread took 11.6 to 12.4 s and 8 threads gained nothing (the work is kernel metadata updates). "In the background" in NFR-PERF-06 means the session does not wait for it (lines wait only under FR-CKP-02); it must **not** mean `PRIO_DARWIN_BG`, whose throttled I/O stretched the same work to 33 to 51 s, nor QoS background, which is documented to apply the same throttling (not run separately). The shadow costs about 340 bytes of metadata per file (29 to 40 MB per 100,000 files), whatever the strategy, and removing it about 5 s. Because the margin is small and cold-cache and slower-machine runs are pending, the shadow builder (KNSH-079) records each build's file count and duration and reports a build over 10 s; the performance validation repeats the measurement with a cold cache. KNSH-079 implements this (`knsh_checkpoint::shadow`, threads lowered with `pthread_set_qos_class_self_np`); a 10,000-file tree on the home APFS volume took 0.89 s through the real clone service (warm cache, macOS 26.6.2). **Fallback to evaluate, not adopted:** one `clonefile(2)` per top-level folder that is not excluded (a whole 100,000-file tree took 1.6 to 1.7 s, 3.7 to 4.4 s in the background band, with identical attributes). Apple's manual "strongly discourages" cloning directory hierarchies with it, a single call cannot be cancelled or skip excluded paths below the top level, and a tree that changes during the call is cloned item by item, so it needs its own spike before use. Clones keep size, `mtime`, birth time, mode, flags, owner and xattrs; setuid and setgid are cleared and hard links are not kept, so a restore from a shadow never re-creates either. |
| 16 | Closing a line's change set, and what dropped file events mean (KNSH-077, C4) | **Proposed.** Flushing alone does not close a line: on macOS 26.6 `FSEventStreamFlushSync` returned in under a millisecond (p50) while 26% to 99.9% of the line's events were still on their way, arriving up to 0.58 s later or never. The watcher (KNSH-080) closes a line this way instead: when the supervisor has reaped the line, it creates a **marker file** in an engine folder on the same volume that the same stream also watches (never inside a root), then calls `FSEventStreamFlushSync` every millisecond until the marker's own event has been delivered. Observed: in every round without a drop flag, with 1, 4 and 16 writers and stream latencies of 0, 0.05 and 0.5 s, every operation of the line had then arrived; 6.6 to 9.3 ms at p50, under 16 ms at p95. In rounds with a drop flag, events still arrived after the marker (36 to 288 ms later) or never. The wait has a clock deadline (proposed 1 s) and also ends when a drop flag arrives (the marker folder receives one too); in 3 of 500 rounds the marker never came. On a drop or a deadline the line's checkpoints are **uncertain** and its roots are rescanned. **Drops:** the stream reported `UserDropped` with `MustScanSubDirs` (`KernelDropped` was not seen) on **each watched path itself**, never on a sub-folder, so the rescan scope is the whole root; 16 concurrent writers (about 2,100 operations per line) caused it in 68 to 93% of lines at every latency tried, 4 writers in 4 to 22%, 1 writer never. Any event carrying `MustScanSubDirs`, `UserDropped`, `KernelDropped`, `EventIdsWrapped` or `RootChanged` between a line's start and its marker makes that window's checkpoints uncertain (FR-CKP-04) and rescans the path the event names; `RootChanged` (seen with `WatchRoot` when a root is renamed away and back) also re-resolves the root. **Flags are not a change log:** per-path flags accumulate (a file's later events still carry `Created`; a created-and-removed file shows `Created\|Removed\|Modified`), and every new file carries `XattrMod` (`com.apple.provenance`), so an event only means "this path may have changed": the watcher `lstat`s it and compares with the shadow. Implemented by KNSH-080 with a 1 s deadline and a 50 ms stream latency ([checkpoints](../03-functional-requirements/checkpoints.md#taking-checkpoints)). |
| 17 | Memory-mapped writes, "possibly torn" and post-image identity (KNSH-077, C3, C4) | **Proposed.** Observed on macOS 26.6: stores through a shared mapping never changed the file's `mtime` or size, not after `msync(MS_SYNC)`, not when the writer exited, and not in the 40 s after (only `ctime` moved, at exit); FSEvents reported **nothing while the writer stayed alive** (40 s, with or without `msync`), and one `Modified` event when it exited and its descriptor was closed. A clone taken while pages were dirty held the dirty data (the clone took 2.4 ms in the recorded run, up to 3.7 ms in earlier unrecorded ones, instead of about 0.2 ms, so the pages are written back first), and a clone taken while a writer kept storing was torn in 195 of 200 tries in the recorded run (197 and 198 in two earlier, unrecorded runs), with up to 182 runs of different generations across its pages; a `pwrite` writer gave a single clean cut. Hence: (1) a change through a live mapping cannot be detected after the fact by size, `mtime` or events, only by comparing content, so FR-CKP-24 is implemented by **observation at line end**: the supervisor lists, for the line's processes and every process still alive in its envelope, descriptors open for writing (`PROC_PIDLISTFDS`, `PROC_PIDFDVNODEPATHINFO`, `FWRITE`) and writable file mappings (`PROC_PIDREGIONPATHINFO`, write protection), which worked for a same-user process without privileges; a system-wide `proc_listpidspath` took 284 to 620 ms per path, too slow per line. A path inside a root held that way by a process that outlives the line is **possibly torn**, and its next event (when the writer closes) is attributed as an agent edit, not to a later line. (2) **Post-image identity** (FR-CKP-09) cannot rely on `mtime` for such files: for files under 64 MB the content hash catches the change; for larger files, undo and redo also refuse (as a conflict) while any process has the file open for writing or mapped writable, checked at restore time. (3) SQLite databases with journals stay possibly torn by name (FR-CKP-24). Implemented by KNSH-085 (`knsh_checkpoint::torn`, `knsh_platform::WriteHolders`): a `MAP_SHARED` region is recognised by its `VM_INHERIT_SHARE` inheritance, since on macOS 26.6 a file mapped shared by one process reports share mode `SM_PRIVATE`, like a private mapping after its first store; unreadable processes mark the whole change possibly torn. Points (1)'s next-event attribution and (2)'s restore-time refusal for large files are still pending ([checkpoints](../03-functional-requirements/checkpoints.md#restore-rules)). |
| 18 | `/dev/tcp` and `/dev/udp` redirections in the native interpreter (KNSH-099, FR-NET-08) | **Refused.** Bash turns `/dev/tcp/host/port` and `/dev/udp/host/port` into a socket the shell itself connects, outside any program the supervisor decides on. The native interpreter makes no connection of its own: such a redirection fails like any other (bash's message form, `…: network redirections are refused: the shell opens no connection of its own (FR-NET-08)`, the command does not run, status 1), in human and agent sessions alike. Not routed through the proxy either: that would give the shell a network path with no command record of its own, and `nc`, `curl` and the like already reach the proxy as recorded commands. Supporting it later needs a decision of its own (a recorded pseudo-command under the line's profile and proxy credentials). The names are matched as bash matches them, on the expanded word's text; any other spelling is an ordinary path, which does not exist on macOS. |
| 19 | Subshells of the native interpreter (KNSH-100, NFR-COMPAT-02) | **Decided: copies, not forks.** Bash forks a process for `( … )`, for each command of a pipeline and for `&`. The native interpreter runs in a multithreaded process (the evaluation thread, a thread per waited child) where `fork` without `exec` is unsafe, and every program must still be started through `CommandSpawner` so KNSH-108 decides on it. A subshell is therefore a copy of the interpreter's state (variables, options, working directory, descriptor table) that shares only the injected effects and the message writers; it runs on the shell's thread (a subshell alone without job control, a simple pipeline stage) or on a thread of its own (a compound stage, a background list, a subshell alone under job control, which reports to the shell when its programs stop so Ctrl-Z stops the job). What a subshell changes never reaches the shell, as in bash. What has no equivalent without a process is refused or documented, never made up: `$!` of a job the shell runs itself is refused (a made-up number could name a stranger's process), and such a job cannot be stopped as a whole ([compatibility](../04-non-functional-requirements/compatibility.md)). |
| 20 | `exec` and the process of the native interpreter (KNSH-101, NFR-COMPAT-02) | **Decided: run, then end the shell.** Bash's `exec cmd` replaces the shell's process with the program. The native interpreter's process may run more than one shell and must start every program through `CommandSpawner` so KNSH-108 decides on it, so `exec cmd` starts the program like any command (with `exec`'s `-a`, `-l` and `-c`, and `SHLVL` lowered as bash lowers it) and the shell ends with the program's status once it ends; a program that cannot run ends a non-interactive shell with 127 or 126, as bash. `$$` in the program is not the shell's. Likewise `cd` changes the interpreter's working directory, never the process's, and every command starts there. |
| 21 | Regular expressions of the native interpreter (KNSH-102, NFR-COMPAT-02) | **Decided: the system's `regcomp` and `regexec`.** Bash's `[[ string =~ regex ]]` compiles with the C library's `regcomp(REG_EXTENDED)` and matches with `regexec`, so the system engine gives bash's answers exactly (bracket expressions, classes, leftmost-longest matches, subexpression offsets) where an in-house engine would differ in corners; it needs no new crate. The calls live in `knsh-platform` (`regex_match`, the only `unsafe` they need), under the locale the shell's `LC_ALL`, `LC_CTYPE` or `LANG` names, installed for the calling thread only (`newlocale`, `uselocale`) and put back after, so other threads never see it. A match that would split a UTF-8 character (the C locale over UTF-8 text) is refused rather than altered. macOS's `regex_t` is declared in `knsh-platform` (the `libc` crate keeps `re_nsub` private) with its size checked against `libc`'s; the Linux backend declares its own. |
| 22 | `echo` in bash's POSIX mode (KNSH-106, NFR-COMPAT-02) | **Decided: as macOS's `/bin/sh`.** Bash 5.2 in POSIX mode keeps `echo`'s options and escapes as `xpg_echo` says (off by default) and drops the options only when `xpg_echo` is on. macOS's `/bin/sh` (bash 3.2 built for UNIX 03) takes no options and interprets escapes in POSIX mode whatever `xpg_echo` says (`sh -c 'echo -n "a\\tb"'` prints `-n a`, a tab, `b`), also after `set -o posix` in `/bin/bash`. The story's target is POSIX scripts behaving as with `/bin/sh` on macOS, so in POSIX mode the native interpreter's `echo` takes no options and interprets escapes; `set +o posix` gives bash's `echo` back. A Linux backend may revisit this for bash 5.2's own behaviour there. |
| 23 | The native interactive shell's line editor (KNSH-107, NFR-COMPAT-02, FR-SES-22) | **Decided: in-house, drawn by redrawing the edited line.** No readline, rustyline or terminfo crate (supply-chain policy). Keys follow readline's default emacs bindings and the basics of its vi keymap; the escape sequences of xterm-compatible terminals (macOS Terminal, iTerm2) are known directly, not read from terminfo, and `.inputrc` is not read (a follow-up). After each key the editing area is redrawn from the start of the prompt's last line (carriage return, clear to end of screen, prompt, line, cursor), which needs only `CR`, `ESC [ n A`, `ESC [ n C` and `ESC [ J`; the screen then shows what readline's incremental redisplay shows, which the PTY test compares with bash's. While a line is edited the terminal's signal characters are read as keys (`ISIG` off): Ctrl-C abandons the line as bash does, and the shell is never stopped or killed by a key typed at its own prompt. Prompt strings are expanded after their escapes as an unquoted here-document's body, which is bash's `promptvars` expansion (parameter, command and arithmetic substitution, no splitting or globbing), escape results being quoted first so they are not expanded again. |
| 24 | Where the native interpreter of an agent line runs, and who starts its commands (KNSH-108, NFR-SEC-02, FR-LC-50 to FR-LC-58) | **Decided: a sandboxed `knsh` process that asks the supervisor for every program.** Running the interpreter inside `knshd` would let a line's redirections and builtins act with the daemon's rights, outside any sandbox; letting the interpreter spawn would put the decision in the process the agent's script drives. So the interpreter runs under its own profile (the session's file rules, no network, no `fork`, exec of nothing but `knsh`) and holds one end of a socket pair: each external command goes over it, with its descriptors, and `knshd` decides it through the phase 2 pipeline and spawns it through `knsh-exec`'s program mode, in the line's process group. A lost channel denies every command. The line itself is recorded with source `native` and no decision of its own; its commands are recorded with `parent_record_id`. Rejected: deciding the whole line as well (the authority would be asked twice, once about the opaque `eval`), and an environment variable naming the channel (the agent controls the environment; the descriptor number is an argument only `knshd` writes). |

## Still open

1. Apple grants the Endpoint Security entitlement case by case. Whether it is granted for a broadly distributed developer tool is not yet known; the application should go in now.
2. Which events the descendant client can authorise beyond exec (file opens, network), and what happens to pending and later operations if `knshd` exits. Verify on macOS 27 before relying on it.

Platform claims to verify before phase 2 are in [../07-testing/verification-claims.md](../07-testing/verification-claims.md).
